# Каналы распространения и безопасные обновления

## Общие правила

- Один открытый код, три варианта: **GitHub**, **Google Play**, **RuStore**.
- Не публикуйте отладочную сборку `*.debug` как релиз: и package name, и ключ отличаются от выпуска.
- Выберите постоянный `applicationId`, сейчас `org.nasedka.app`, до первого публичного релиза; убедитесь, что он свободен и подходит для ваших прав на имя.
- Обновление Android принимается при прежнем `applicationId`, подходящей подписи и неуменьшающемся `versionCode`. Увеличивайте `versionCode` в каждом релизе.
- Закрытый ключ подписи должен храниться у владельца проекта и в защищённых GitHub Secrets, но **никогда** в публичном репозитории или в чате.
- Google Play App Signing может использовать другой ключ подписи, нежели GitHub APK. Не обещайте бесшовных переключений между магазинами без согласованной стратегии ключей.

## GitHub (внедрена базовая логика)

1. Создайте публичный репозиторий и опубликуйте код, а в настройках приложения укажите `owner/nasedka-android`.
2. Делайте **только подписанные** стабильным ключом release APK. Приложите файл с точным именем `nasedka-github.apk` к GitHub Release с версией в формате `vX.Y.Z`. GitHub должен возвращать `digest: sha256:...`.
3. Приложение сравнит numeric release tag с текущей версией, покажет кнопку при наличии более новой, загрузит APK через Android DownloadManager.
4. После скачивания пользователь открывает **Настройки → Обновления → Продолжить установку APK**. Приложение сверит SHA-256 и передаст файл системному установщику Android через FileProvider.
5. Android попросит разрешение на установку приложений из этого источника и проверит сертификат. Установка не бесшумная и не обходит системные подтверждения.

При отсутствии файла, SHA-256 или корректного репозитория установку не предлагаем. Сетевая ошибка **не блокирует** инкубационные напоминания.

## Google Play (подготовлено разделение, SDK впереди)

- Google Play запрещает самостоятельную установку APK обновлений из другого источника: `https://support.google.com/googleplay/android-developer/answer/16559646`.
- Следующий шаг — **Google Play Core In-App Updates**, предпочтительно гибкие обновления: `https://developer.android.com/guide/playcore/in-app-updates`.
- До подключения SDK в этой сборке есть только переход на страницу Google Play; **встроенная загрузка и установка магазинной версии не реализованы**.
- Начиная с 31.08.2026 новые приложения и обновления должны использовать целевой Android API 36+: `https://support.google.com/googleplay/android-developer/answer/11926878`.
- Понадобятся AAB, Play Console, описание сбора данных, политика конфиденциальности, пользовательское тестирование и проверка правил рекламы.

## RuStore (подготовлено разделение, SDK впереди)

- RuStore предоставляет **In-App Updates SDK**, включая гибкий режим скачивания и последующее подтверждение установки: `https://www.rustore.ru/help/sdk/updates`.
- Для SDK может понадобиться регистрация приложения в консоли, соответствующая подпись/пакет, актуальный RuStore на телефоне и авторизация пользователя.
- До интеграции SDK текущая сборка открывает страницу магазина. Встроенное магазинное обновление **ещё не реализовано**.
- После публикации сверяйте сроки модерации, подписи, разметку рекламы и требования RuStore: `https://www.rustore.ru/help/developers/publishing-and-verifying-apps/app-publication`.

## Проверка на устройствах перед релизом

Нужны два последовательно подписанных APK с одним `applicationId` и одним сертификатом: 0.2.0 → 0.2.1. Убедитесь, что приложение замечает выпуск только при более новой версии, проверяет SHA-256, не устанавливает повреждённый файл, не удаляет журнал и после обновления восстанавливает уведомления. Без этих тестов обновления нельзя считать готовыми.

**Открытый проект не требует открытой публикации секретов подписи.**
