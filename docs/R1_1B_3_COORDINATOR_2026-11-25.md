## 3. Контракт DataAccessCoordinator (предлагаемая реализация -3b)
Один экземпляр на Application/process, не на Activity. Admission mutex держать только при изменении метаданных, никогда во время DB/SAF/Android service или пользовательского callback. Состояния STARTING, READY, SHORT, SNAPSHOT, RESTORE, RECOVERY_REQUIRED. STARTING и RECOVERY_REQUIRED не дают обычным входам разрешение. SHORT — один логический read/write/render callback, не один SQL; все Db/FarmDb/cursor handles закрыты до выхода. Только текущий владелец может вложенно войти в совместимый SHORT без нового ожидания; outer lease завершает операцию. Не позволять upgrade SHORT→RESTORE, не передавать thread-bound lease. Неверный/двойной release не переводит coordinator в READY. Исключение в обычной операции освобождает её после закрытия ресурсов; restore/recovery exception по умолчанию RECOVERY_REQUIRED, не READY. Успех restore/recovery только после подтверждённого согласованного outcome и durable NONE; scheduler failure не откатывает уже committed data.

Резервирование тяжёлой операции происходит атомарно на принимающем потоке (без передачи ReentrantLock между потоками): одноразовый reservation/ticket для SNAPSHOT/RESTORE, затем worker claim, thread-bound lease. Пока ticket ожидает worker, новые SHORT/backup/restore не допускаются; executor rejection отменяет только не начатую reservation с проверкой identity, не меняет уже начатое восстановление. При сбое выполнения после начала — fail closed. Worker не зависит от жизни Activity. Не ждать занятость из main thread или BroadcastReceiver. Никаких blocking wait, бесконечного goAsync или захвата scheduler monitor до coordinator. UI короткие операции пока могут оставаться синхронными как в текущем коде; это не обещание отсутствия ANR, отдельно измерить.

Порядок: admission/owner context → logical operation → helpers/prefs → Android scheduling side effects, без обратного входа с чужого потока. Устранить static synchronized scheduler после подтверждения единой границы, или строго coordinator-before-monitor в переходной версии; не оставлять два конкурирующих lock-order. Повторный render после worker release допускается новой операцией. Не держать lease пока пользователь выбирает файл, вводит данные, открывает диалог или пока идёт сеть.

## 4. Поколение данных и отложенные входы (-3c)
Локальный UUID поколения (например внутренний ключ data_generation); не batch ID и не UUID journal самой операции. Первое существующее поколение инициализировать проверенным commit под STARTING до READY, не переписывать при каждом запуске; каждый restore получает новый UUID независимо от импортируемого файла. Добавить old/new generation к canonical managed prefs snapshot с явным версионированием формата; не менять public JSON v1, не принимать generation из пользовательского файла. Зафиксировать совместимость прежнего внутреннего формата и прежних тестовых snapshot; неизвестная версия fail closed. ROLLED_BACK возвращает старый token; COMMITTED — новый. Обязателен проверенный commit/readback, pending apply обычных prefs согласовать перед snapshot; не считать cached read после false commit доказательством долговечности. Generation и scheduler watermarks остаются в одном restore transaction; служебные unrelated prefs сохраняются.

Проверять generation внутри уже полученного owner context, не до него (TOCTOU). PendingIntent identity (URI, action/requestCode) должна различать поколения, а не только extra: FLAG_UPDATE_CURRENT обновляет существующий token. Старые unversioned DONE/SNOOZE/FIRE/TICK не выполняют запись/показ на новом поколении; rolling alarm переустановить, отменять известные старые identities безопасно, не зависеть от успешной отмены всех старых snooze. Notification open с устаревшим batch_id ведёт на нейтральный экран, не к записи нового ID. Не доверять exported launcher extras. Farm tick и content intents тоже versioned; системные BOOT/time/package intent валидировать по allowlist; диагностический TEST отделён от данных.

Формы/диалоги и SAF picker: capture generation при показе/запуске, проверка при сохранении/возвращении результата; ещё in-memory view epoch для устаревшего UI после restore/rollback. Не менять Bundle ID без проверенной пары generation, не терять черновик незаметно: при busy/stale показать отказ и сохранить введённое до явного повторного открытия/решения пользователя; полноценное сохранение черновиков R1.2 не подменять. Действия пользователя DONE/SNOOZE при busy — не отмечать выполненным, не dismiss, явное сообщение и доступный повтор; обязательные тесты, при невозможности доказать retry — спроектировать durable очередь до допуска. Не replay устаревшие действия. Rolling tick/boot/reschedule coalesce в bounded flag и реконструировать после READY; не продвигать watermark при busy. При process death флаг не доказуемо durable: STARTING обязан выполнить повторное планирование, данные задач остаются в DB. RemoteFeed/cache writes либо короткая admission после сети, либо явный retry/drop только disposable cache, не учётное действие.

## 5. Startup / integration (-3c/-3d)
Application прежде любого открытия live helper устанавливает STARTING. Recovery worker проверяет root/legacy/v2 состояния, не создаёт пустые DB при unresolved/missing original. Различать подтверждённо fresh install (нет обоих DB и restore evidence) и недостающую/неоднозначную пару; существующая одиночная БД возможна при нормальном первом использовании, поэтому нужен отдельно проверенный migration/initialization policy, не удалять и не объявлять её повреждённой автоматически. Не открывать Db/FarmDb при PENDING/COMMITTED/ROLLED_BACK: сначала RestoreLegacyRecovery при отсутствии конфликтующего v2 или RestoreProtocol.recover; проверка durable NONE, затем normal init/migrations. Work directory creation/sync и root absence должны быть явными. Старый marker без доказуемого исходного состояния — блокировать, хранить файлы. Не переносить прежний destructive BackupStore.recover в новый startup. UI в STARTING/RECOVERY_REQUIRED не делает render бизнес-данных; нейтральное сообщение/повтор восстановления, без автоматической очистки и без публичных путей/данных. Export/restore worker под Application coordinator; valid SAF parse outside; подготовка реальных схем и relations, checkpoint/close, private previous JSON, immutable copies и generation только после exclusive claim. Не менять источники до PENDING. Отвязать CSV/SAF write от DB handle. Последовательность всех входов A01–A13 внедрять в одной рабочей ветке; неполный guard не выпускать.
