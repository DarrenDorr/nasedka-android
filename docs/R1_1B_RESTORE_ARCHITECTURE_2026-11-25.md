# R1.1b — согласованное резервное копирование и аварийное восстановление

Дата: 25.11.2026. Проект реализации, не доказательство исправления. Основание: R1-F01/F02, B02–B05 в [R1 audit](R1_RELIABILITY_AUDIT_2026-11-25.md), D-009/D-020/D-021/D-028. База: PR #7, commit 062c8b4af76e35aa00d5779a77265d462a55644d; R1.1a PASS в проверенном объёме на 02afaf7, 10/10 Android tests. На момент проектирования финальный повтор SQLite на 062c8b4 ещё выполнялся (run 45533839632); интеграция R1.1a обязательна до изменения production Java. Этот документ не входит в PR #7.

## 1. Цели и неизменяемые условия

- Снимок обеих локальных SQLite и переносимых настроек отражает одно согласованное логическое состояние. Прерывание восстановления приводит либо к исходному состоянию, либо к полностью проверенному новому поколению, не к смешению данных.
- Не менять утверждённый UI, схемы SQLite v2, формат публичного backup JSON v1, пользовательские правила учёта и регистрацию. Не добавлять облако или сторонние службы. Две базы остаются раздельными.
- Восстановление по-прежнему заменяет, а не объединяет историю, после явного подтверждения. Файл из SAF недоверенный; R1.1a validation остаётся обязательным.
- Никаких испытаний на единственной рабочей копии. Никакого утверждения о надёжности при аппаратном повреждении накопителя: контролируемое исключение, process death и имитация сбоя питания — разные модели.

## 2. Фактический исходный риск

В BackupStore.snapshot последовательные SELECT из двух файлов, затем settings; backup/restore выполняются из MainActivity в Thread, но UI и receivers продолжают обращаться к Db/FarmDb. synchronized у BackupStore не защищает другие компоненты. switchBoth удаляет marker и прежние базы до SharedPreferences.commit(), не проверяя boolean. Старый marker содержит лишь rollback_if_interrupted. NasedkaApplication вызывает recover до открытия БД. Это проверено чтением текущих исходников; эффекты аварии пока не воспроизведены.

## 3. Предлагаемый координатор доступа

Выбор для первого варианта — единый внутрипроцессный эксклюзивный барьер на уровне **полной логической операции**, а не отдельных SQL вызовов/отдельных helper. Изоляция должна охватывать UI-обработчик, связанное чтение/запись обеих БД, настройки, сохранение, экспорт CSV, оба scheduler и все receiver paths. Проверить наличие иных процессов в manifest; при будущих отдельных process потребуется межпроцессная синхронизация, текущий механизм её не обещает.

- Ввести один coordinator с состояниями READY / BACKUP / RESTORE / RECOVERY_REQUIRED. Сначала inventory всех входов и тесты владения, реентерабельности и порядка блокировок. Не вводить новый lock в отдельные методы, сохраняя противоположный порядок существующих synchronized scheduler; сначала устранить инверсию lock-order.
- Долгие операции выполняет рабочий поток. UI не ждёт блокирующий lock: доступные операции отклоняются с понятным состоянием занятости/планируются после завершения; визуальный каркас не меняется. При уходе Activity нельзя снять барьер до завершения backend. Второй restore и экспорт в тот же момент не начинают замену.
- Receiver не должен держать главный поток заблокированным и не должен бесследно терять DONE. Определить ограниченный по времени механизм defer/replay с durable intent либо явным отказом и возможностью повторного действия; перед replay проверять поколение данных. До проверки всех входов barrier не считать готовым. Не использовать indefinite goAsync; учитывать лимиты Android.
- Экспорт: захватить барьер, дождаться закрытия открытых handles (все ресурсы try-with-resources), создать согласованный снимок и получить неизменяемые bytes; запись SAF выполнять после освобождения барьера, если не меняется снимок. Для restore пользовательский файл можно прочитать и структурно проверить до барьера, но с момента проверки текущих данных/создания rollback до конца операции доступ эксклюзивный.
- Системные разрешения и каналы уведомлений не являются частью переносимой копии. Перепланирование после восстановления выполняется отдельно и повторяемо, не должно превращать подтверждённую замену данных в ложный rollback.

## 4. Журнал транзакции восстановления (предлагаемый внутренний протокол v2)

Не путать внутренний журнал восстановления с публичным форматом backup v1. Один ID поколения на операцию, фиксированные пути внутри sandbox (никаких пользовательских путей из JSON).

| Фаза | Действие | Устойчивое состояние после сбоя |
|---|---|---|
| PREPARE | Под барьером проверить лимит/свободное место, сформировать и проверить обе staging DB, integrity + relations, checkpoint и закрытие всех handles. Подготовить синхронизированные неизменяемые rollback-копии обеих файлов и переносимых настроек, сохранить исходное поколение | Рабочие данные не изменены; временные файлы можно очистить |
| PENDING | Атомарно записать внутренний журнал с ID, версией, именами фиксированных файлов, контрольными суммами старых копий, old prefs и target prefs; подтвердить durable write до замены | Recovery откатывает к старому поколению |
| APPLY | Заменить обе БД из staging (отдельные атомарные rename на одном filesystem, сохранить rollback-копии), удалить/проверить sidecars только после checkpoint/close, записать настройки и generation marker через проверенный commit() | При сбое/commit false — PENDING, восстановить старые базы и настройки |
| VERIFY | Проверить новое состояние обеих БД, ожидаемые настройки и целостность; только после успеха атомарно записать COMMITTED | PENDING означает rollback; COMMITTED означает принять новое поколение |
| CLEANUP | После durable COMMITTED удалить временные/rollback-файлы, затем журнал. Уборка идемпотентна | COMMITTED recovery не откатывает подтверждённое новое состояние; повторяет cleanup |

Подробности реализации: временные файлы на том же filesystem; fsync данных и, где поддерживается, directory metadata после публикации/rename. Использовать атомарную запись (например Android AtomicFile с проверкой результата и синхронизацией); не обещать гарантии при отключении питания до проверки реального поведения. Rollback восстанавливает из копии через отдельный временный файл, не уничтожает последнюю исправную копию до подтверждённого завершения. Если любой rollback шаг не удался, сохранять PENDING и доказательства, закрыть обычный доступ, сообщить о невозможности безопасно открыть данные; не создавать пустые базы и не удалять данные. Не выводить внутренние пути/содержимое пользовательских записей в публичные логи.

Проверить отдельно совместимость старого marker rollback_if_interrupted: не интерпретировать как COMMITTED, выполнить прежний безопасный recovery по наличию оригиналов либо fail closed при неопределённости. Не удалять исторические резервные файлы без доказанной принадлежности к операции.

Старые уведомления с тем же batch_id после restore могут относиться к другой партии. Минимальный guard поколений для отложенных/старых действий — часть защиты R1.1b; полная переработка snooze/watermark остаётся R1.3. Старые PendingIntent без версии должны быть обработаны явно (не применять к новым данным), перепланировать оба scheduler. Не удалять подтверждённые учётные факты.

## 5. Испытания и критерии

Ввести test-only failure injection на уровне абстракции storage/commit, без доступного production интерфейса для вызова сбоев. Начать с модели переходов и детерминированного harness; затем реальная Android SQLite и файловая система в отдельном временном каталоге. Имитация exception не равна process kill; отдельный сценарий abrupt kill/restart и доказательство повторного recovery.

| ID | Подслучаи | Ожидание |
|---|---|---|
| B02 | Запись UI/межтабличного движения, DONE, настройки в момент snapshot; coordinated interleaving через latch | Снимок полностью до или после операции; все 14 таблиц + prefs и связи согласованы |
| B03 | До PENDING; после durable PENDING; после каждой замены; перед/после prefs commit; перед/после COMMITTED; во время cleanup; повторное прерывание rollback | До COMMITTED старое поколение; после COMMITTED новое; recovery повторяем; обе базы + prefs согласованы; ни одна база не пуста по умолчанию |
| B04 | ENOSPC на staging, записи rollback/журнала, переименовании; I/O exception; prefs.commit false; сбой rollback | До destructive phase отказ без изменения; после — доказанный откат либо fail closed с сохранением источников |
| B05 | Два restore, export/restore, UI и оба receiver, смена Activity; old notification с совпадающим ID | Только одна операция меняет поколение; нет гонок, stale writes или потерянных подтверждённых действий; старые уведомления не меняют новое поколение |
| B01-reg | Все существующие 10 R1.1a Android tests + полный изолированный backup/restore round-trip через файловый/SAF harness | Не регрессирует validation, обе БД, ссылки, settings, история |
| B08 | Недоступный SAF, отмена, прерывание записи | Рабочие данные целы; неполный экспорт не объявляется пригодным |

Статус всех новых кейсов NOT_RUN. Для допуска: JVM и три flavor build PASS, существующие Android тесты PASS, новые тесты на Android и фактический отчёт XML, evidence по каждой точке отказа, проверка lock-order и всех входов. B08 физический provider и настоящий APK upgrade M03 могут потребовать R1.4; не выдавать их за PASS. Результаты хранить с commit, run IDs, API, hashes, фактическим/ожидаемым состоянием, без реальных данных.

## 6. Очередь реализации

R1.1b-0 — этот план и inventory входов, без изменения production кода.
R1.1b-1 — протокол состояний и test-only fault model, tests first.
R1.1b-2 — файловый recovery и настройки: durable marker, rollback, commit/cleanup, legacy compatibility, isolated Android tests.
R1.1b-3 — coordinator, полный охват UI/receiver/backup/settings, generation guard, тесты конкурентности.
R1.1b-4 — полный round-trip, regression, контрольный отчёт. Не включать частично защищённый restore в main до совместной проверки -2/-3.

Следующий конкретный шаг после интеграции R1.1a: R1.1b-1, спроектировать интерфейс хранения и тесты state machine для всех фаз и отказов. Не менять UI и базы до этого. R1.1b implementation NOT_STARTED; пользовательские данные и релиз не допускаются.
